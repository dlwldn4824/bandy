# 밴디 실사용(운영) 전환 체크리스트

데모(브라우저 저장소)가 아니라 실제 사용자에게 열기 전에 해결할 것. 2026-11-17 독립 검토(3차) 결과를 바탕으로, 이미 코드로 고친 것은 따로 표시했다.

구분: **시범 전 필수** = 12월 시범 공연 전에 반드시 / **정식 오픈 전** / **나중**

## 1. 사람이 설정·결정해야 하는 것 (코드로 못 함)

| 항목 | 구분 | 할 일 |
|---|---|---|
| Supabase 연결 | 시범 전 필수 | Project URL · anon key를 배포 환경변수(`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`)에 넣고 migration 적용. service role 키는 절대 앱에 넣지 않음 |
| 데모 배포 | 시범 전 필수 | 운영 빌드는 키가 없으면 '서버 설정이 빠졌어요' 화면이 뜸. 시연용 배포만 `VITE_BANDY_DEMO=true` |
| pg_cron | 시범 전 필수 | Database → Extensions에서 pg_cron을 켠 **뒤** migration 실행(또는 다시 실행). 그래야 입금 기한 정리가 10분마다 돎 |
| Auth 주소 | 시범 전 필수 | Supabase Auth → URL Configuration의 Redirect URLs에 `https://<도메인>/app/**` 등록(카카오 로그인 복귀, 가입 인증 메일, 비밀번호 재설정) |
| 카카오 로그인 | 시범 전 필수(쓸 거면) | 카카오 개발자 앱 생성, 동의 항목(이메일·닉네임), Supabase Auth 제공자에 키 등록 |
| 운영자 지정 | 시범 전 필수 | 지금은 SQL로만: `update public.profiles set is_admin = true where id = '<사용자 id>';` 누가 운영자인지 기록해 둘 것 |
| 개인정보 처리방침·동의 | 시범 전 필수 | 수집 항목: 이름, 이메일, 입금자명, 환불 계좌(환불 완료 시 삭제), 감사 기록. 보관 기간, 공연 입금 계좌가 공개된다는 점(동아리 대표 개인 계좌일 수 있음) |
| 백업 | 시범 전 필수 | 무료 플랜은 시점 복구(PITR)가 없음 → 유료 플랜 또는 정기 `pg_dump` |
| 입금 운영 규칙 | 시범 전 필수 | 오입금(이름 다름)·부분 입금·초과 입금은 앱에 기능이 없음 → 동아리가 확인 전에 직접 연락하는 규칙 문서화 |
| 앱 밖 공지 | 시범 전 필수 | 알림은 앱 안에만 감. 일정 변경·공연 취소는 동아리가 오픈채팅 등으로도 공지 |
| 오류 수집 | 시범 전 필수 | Sentry 등 연결(지금은 브라우저 콘솔에만 남음) |

## 2. 코드로 남은 일

| 항목 | 구분 | 내용 |
|---|---|---|
| 데이터 조회 방식 | 시범 전 필수 | 지금 13개 테이블을 통째로 읽음 → Supabase 기본 응답 상한(1000행)을 넘으면 조용히 잘림. 화면별 조회·페이지 나누기로 바꿔야 함(Supabase 연결 때 함께) |
| 이미지 저장 | 시범 전 필수 | 포스터·프로필을 data URL로 DB에 저장 중 → 조회마다 모든 이미지를 받음. Supabase Storage 업로드로 |
| 지도 좌표 | 정식 오픈 전 | 주소 → 좌표 변환(카카오 Local) 미연결. 시범은 지도 숨김 또는 수동 좌표 |
| 실제 알림 발송 | 정식 오픈 전 | 카카오 알림톡 또는 웹 푸시(iOS는 홈 화면 앱에서만) |
| 회원 탈퇴 | 정식 오픈 전 | 계정·개인정보 삭제와 진행 중 예매·환불 처리 규칙 |
| 운영자 도구 | 정식 오픈 전 | 분쟁(입금했는데 확정 안 됨), 정지 해제, 감사 기록 조회, 입금 대조용 목록 내보내기 |
| rate limit | 정식 오픈 전 | 예매·동아리 등록·교류 신청 횟수 제한, Supabase Auth 제한 설정 |
| 서비스 워커 | 정식 오픈 전 | 지금 오프라인 QR은 '한 번 열어 둔 티켓'만. 앱 자체를 오프라인으로 여는 건 안 됨 |
| 공유 미리보기 | 정식 오픈 전 | `/app/e/:id` 링크 미리보기가 기존 서비스 기본값으로 나옴 |
| 데모 코드 정리 | 나중 | LocalBackend·repo.ts(서버 규칙 복제본)·seed. 남길 거면 서버=데모 자동 비교 테스트 |

## 3. 논의 중 (결정 필요)

- 계좌이체 온라인 예매 마감 시각: 지금은 공연 시작까지. 현장 판매와 나눌지(시장 조사 후 결정). 정해지면 공연마다 '판매 마감' 입력으로 바꿀 수 있음(`ticket_types.sales_ends_at`)
- 확정 예매의 환불: 지금은 공연 취소·일정 변경 때만 예매자가 요청 가능. 단순 변심 환불 허용 여부·기한
- '유지'를 고른 뒤 다시 환불 요청 허용 여부(지금은 공연 시작 전까지 허용)
- 운영진(MANAGER)의 하단 바 '내 티켓' 버튼(구조도는 회원 유형별 교체)

## 4. 이번 검토에서 이미 고친 것 (참고)

- '입금했어요'만 누르고 입금하지 않아 자리를 영원히 잡던 문제 → 기한 + 24시간(공연 끝까지) 뒤 만료, 3번까지, 공연당 입금 대기 1건
- 현장 입금 확인 불가 → 입금 기한 = 3일과 공연 끝 중 빠른 쪽(예매는 공연 시작에 마감)
- 환불 요청과 입장 처리가 동시에 성립 → 티켓 잠금(30회 시험 0건)
- 공용 기기에서 앞 사람 입금자명·QR이 남음 → 계정이 바뀌면 기기 정보 삭제
- 환불 계좌 노출 → 결제 정보는 예매자와 주최 운영진만, 환불 완료 시 계좌 삭제
- 장소 띄어쓰기만 고쳐도 '일정 변경' → 같은 장소로 판단, 변경 창에 이전·변경 일정 표시
- 운영 빌드에서 조용히 데모로 열림 → 설정 오류 화면, 데모는 명시해야 함, 데모 화면에 '시연용' 표시
- 기존 서비스 화면에서도 밴디 코드·Supabase 클라이언트가 만들어짐 → `/app`에서만 불러옴
- 캐시 헤더(`vercel.json`), 비밀번호 재설정, 가입 인증 메일 복귀 주소, 예금주 직접 입력, 아이폰 하단 여백, 카카오톡 인앱 브라우저 안내, 자정 넘는 공연 표시, 끝난 공연 QR 차단, QR 요청 6초 시간 초과 후 저장된 QR 표시

# Bandy 모바일 기능 추가 개발계획서

작성일: 2026-10-07 · 상태: 팀 검토용 초안

근거 문서: [밴디 기능 추가](https://app.notion.com/p/3f0b2368087980878fa2f2efb1e0ae58), 문서 날짜 2026-10-05.

Claude가 계획 구성과 요구사항 검토를 주도했고, Codex가 원문과 대조해 역할·범위·표현을 정리했다. 이 문서는 본인의 백엔드 개발 방향과 작업 순서를 정한다. 본인이 개발계획서에 이어 API 명세서·외부 API 검토·데이터 흐름·DB 구조 설계를 담당한다. Supabase 프로젝트 생성·설정·배포는 우리 담당이 아니다. API 경로·함수명·DB 테이블은 설계안이며 팀 연동 시 확정한다.

표시 기준: **[원문]**은 노션에서 확인한 내용, **[제안]**은 팀이 검토할 구현 순서·완료 기준, **[미정]**은 확정되지 않은 내용이다. 원문에 있는 기능도 구현·일정이 확정됐다는 뜻은 아니다.

## 1. 목표와 역할

### 개발 목표 [원문]

관객이 공연 탐색부터 예매·결제, 티켓 확인, QR 입장까지 이용하고, 같은 예매·입장 정보가 공연을 주최한 동아리의 관리 화면에 반영되도록 한다. 입장 완료 후에는 기존 서비스의 공연 정보로 연결한다.

### 작업 분담 [사용자 지정]

| 담당 | 맡을 작업 | 산출물 |
|---|---|---|
| 본인: 백엔드 담당 | 개발계획서, API 명세·함수명 규칙, 외부 API 검토, 데이터 흐름, DB 구조 설계, API와 DB 구조 정합성 확인 | 개발계획서, API 명세서, 외부 연동 목록, 데이터 흐름도, ERD·테이블 정의 |
| 유성님 | 구체적인 담당 범위는 미정. 팀에서 별도로 정한다 | 미정 |
| 팀 | 기능·정책과 프론트 연동 조건 협의, 일정 확정 | 합의된 요구사항과 연동 일정 |
| Supabase 세팅 담당 | 우리 담당이 아님. 담당자 이름은 미정 | 프로젝트 생성·설정·배포·실제 연결 확인 |

본인이 백엔드 담당이다. 프론트 담당과 추가 구현 분담, 유성님의 구체적인 역할은 아직 확정하지 않았다. 아래 단계의 일정과 연동 분담은 팀이 확정한다.

## 2. 개발 범위

### 모바일 구현 범위 [원문]

- 로그인: 개인·동아리 회원에 따른 홈 UI 분기. 동아리 회원도 개인 회원 기능을 이용한다.
- 홈: 공연 검색, 알림, 홍보 공연 카드, 실시간/최신 공연 소식, 하단 메뉴.
- 공연 탐색: 목록·검색·필터, 지도·캘린더, 공연 상세.
- 예매: 티켓 종류·수량 선택, 예매·결제, 예매 완료, 티켓 발급.
- 내 티켓: 입장 시간이 가까운 티켓부터 확인하고, 티켓 선택 시 QR을 바로 표시한다.
- 입장: 공연진의 QR 스캔·검증·입장 처리. 입장 완료 후 기존 서비스로 연결한다.
- 동아리 기능: 동아리 등록 진입, 공연 등록·수정·삭제, 동아리 프로필·이미지 관리, 내 공연 목록, 예매자 관리, QR 입장 관리.
- 마이페이지: 개인 프로필, 예매·티켓 내역, 알림·계정 설정. 동아리 회원은 동아리 프로필과 공연 관리에도 접근한다.
- 나머지 기존 모바일 기능은 유지한다. 기존 서비스와의 구체적 재사용·연동 범위는 확인이 필요하다.

### 보류·후속 범위 [원문]

| 항목 | 현재 취급 |
|---|---|
| 동아리 찾기 | 서두에 필요성 검토·보류가 적혀 있다. 뒤쪽 상세 흐름은 참고 자료로 두고, 초기 착수 여부는 재확인한다. |
| 네트워킹·NFC | 이후 추가 기능. 초기 개발·완료 기준에 포함하지 않는다. |
| PC | 모바일 구현 완료 후 시작한다. 이번 계획은 모바일 단계까지 구체화한다. |

## 3. 사용자 흐름과 기능별 결과

### A. 로그인과 권한

**[원문]** 로그인 → 회원 정보·회원 유형 확인 → 개인 또는 동아리 홈. 동아리 계정에는 공연 추가·동아리 등록 등의 `+` 진입을 표시한다.

**[제안] 완료 기준:** 개인 계정과 동아리 계정의 기능 접근이 구분된다. 본인 티켓·예매 내역은 본인만 조회하고, 동아리의 공연·예매자·입장은 관리 권한이 있는 사용자만 다룬다. 화면의 버튼 표시와 서버의 권한 처리 결과가 일치한다.

**[미정]** 회원 유형을 정하는 방식, 동아리 소속·등록 절차, 공연진의 관리 권한을 부여하는 방식. 별도의 스태프 계정 종류가 필요한지는 아직 정하지 않는다.

### B. 공연 탐색

**[원문]** 홈/검색/목록 또는 지도·캘린더 → 공연 선택(`eventId`) → 공연 상세 → 예매.

- 검색·목록: 검색어, 날짜·장소·장르 필터.
- 지도: 위치·반경 기반 공연 조회 → 공연 상세.
- 캘린더: 날짜 선택 → 해당 날짜 공연 목록 → 공연 상세.
- 상세: 공연명·일시·장소·포스터·설명·주최 동아리·티켓 정보 표시.

**[제안] 역할 구분:** 목록·검색은 조건으로 공연을 찾고, 지도는 위치, 캘린더는 날짜를 기준으로 탐색한다. 화면의 구분/통합 방식은 팀이 확정한다.

### C. 예매·결제·티켓 발급

**[원문]** 공연 상세 → 티켓 종류·수량 선택 → 예매·결제 → 예매 완료 → 내 티켓. 완료된 예매는 해당 공연을 주최한 동아리의 예매자 목록에도 반영된다.

**[제안] 완료 기준:**

- 유료 예매는 결제 승인 결과에 맞게 예매·티켓 상태가 바뀐다. 실패하거나 완료되지 않은 결제를 성공 예매로 표시하지 않는다.
- 성공한 예매의 종류·수량과 발급된 티켓 결과가 일치한다. 개인의 내 티켓과 동아리 예매자 목록이 같은 결과를 보여준다.
- 같은 결제 결과를 재수신해도 예매·티켓이 중복 생성되지 않는다.
- `eventId`를 기준으로 예매와 주최 동아리의 관리 화면이 연결된다. 별도 목록을 서로 다르게 관리하지 않도록 API·DB 설계에서 관계를 명확히 한다.

**[미정]** 원문 흐름에서 `bookingId` 생성 시점이 일관되지 않으므로, 생성·상태 변경 시점은 API·DB 설계에서 맞춘다. 무료 공연 지원 여부와 처리 방식, 수량별 티켓 발급 단위는 아직 확정하지 않는다.

### D. 내 티켓·QR 입장

**[원문]** 내 티켓 → 티켓 선택 → QR 바로 표시 → 공연진 스캔 → 검증 → 입장 처리 → 기존 서비스의 공연 정보.

- 내 티켓은 입장 임박/다가오는 공연/이후 공연/사용 완료 순으로 확인할 수 있다.
- QR 검증 결과는 `valid`, `invalid`, `alreadyCheckedIn`을 구분한다.
- 입장 처리 시 `checkInStatus`와 `checkedInAt`이 기록된다.

**[제안] 완료 기준:** 유효한 해당 공연의 티켓만 입장 처리된다. 중복·동시 스캔으로 같은 입장 기록이나 집계가 중복되지 않는다. 입장 결과가 개인 티켓 상태, 동아리 예매자 목록, 입장 수에 일치하게 반영된다.

**[미정]** 입장 임박의 시간 기준, 재입장 정책, QR 방식, 여러 장의 입장 단위, 입장 후 기존 서비스로 넘어가는 화면·식별자·인증 연결 방식.

### E. 동아리 운영

**[원문]** 동아리 로그인 → 동아리 등록/공연 등록 진입 → 공연 정보 입력 → 내 공연 목록 → 공연 관리 → 예매자 목록·QR 입장 관리. 동아리 프로필과 공연 정보를 수정할 수 있다.

**[제안] 완료 기준:** 등록한 공연이 일반 공연 조회와 동아리의 내 공연에 함께 나타난다. 예매 수·입장 수가 예매자 목록의 상태와 일치한다. 다른 동아리의 관리 권한을 임의로 행사할 수 없다.

**[미정]** 동아리 회원에게도 개인 기능은 유지돼야 하지만, 일부 원문 메뉴에서는 내 티켓 대신 공연 등록을 배치한다. 동아리 회원의 본인 티켓 진입 경로를 확정해야 한다. 예매가 있는 공연의 수정·삭제 정책도 정해야 한다.

## 4. 필요한 데이터 — 본인의 API·DB 설계 입력

아래는 **[원문]에서 확인한 화면·흐름별 데이터**다. 테이블 목록이나 API 응답의 확정 형태가 아니다. 필드 명칭·형식·관계는 본인이 API 명세와 DB 설계에서 통일한다.

| 기능 | 필요한 데이터·조건 |
|---|---|
| 로그인·회원 유형 | `userId`, `userType`; 동아리 회원은 `clubId`. 로그인·프로필의 구체적 필드와 인증 방식은 미정 |
| 홈·검색·필터 | 검색어 `query`, 날짜·장소·장르, 공연 목록. 홍보·최신 소식·알림의 세부 필드는 미정 |
| 공연 상세 | `eventId`, `eventName`, `eventDate`, `eventTime`, `location`, `posterImage`, `description`, `clubId`, `clubName`, `ticketInfo` |
| 공연 등록 | `clubId`, 공연명·설명·날짜·시간·장소·티켓 정보·포스터. 등록 결과는 `eventId` |
| 예매·결제 | `userId`, `eventId`, `ticketTypeId`, `quantity`, `orderId`, `paymentId`, `bookingId`, `ticketId`, `bookingStatus` |
| 개인→동아리 예매 반영 | `eventId`, `userId`, `ticketId`, `bookingId`, `bookingStatus` |
| 내 티켓 | `ticketId`, `eventId`, `eventName`, `eventDate`, `eventTime`, `ticketType`, `seatInfo`, `checkInStatus` |
| QR·입장 | `ticketId`, `eventId`, `userId`, `qrToken`, `ticketType`, `seatInfo`, `checkInStatus`, `checkedInAt`, 검증 결과 |
| 동아리 내 공연 | `eventId`, `eventName`, `eventDate`, `bookingCount`, `checkInCount`, `status` |
| 예매자 목록 | `userId`, 이름, `ticketId`, `ticketType`, `bookingStatus`, `checkInStatus` |
| 동아리 프로필 | `clubId`, `clubName`, `introduction`, `profileImage`, `snsLink` |
| 지도·캘린더 | `latitude`, `longitude`, `radius`; `selectedDate`, 공연 목록과 `eventId` |
| 마이페이지 | 회원 정보, 본인의 예매·티켓 내역; 동아리 회원은 동아리 정보·관리 화면 연결. 알림·계정 설정 필드는 미정 |

`ticketInfo`의 세부 구성, 좌석 사용 여부, 상태 값, 장르 정보, 동아리 최초 등록 항목은 원문만으로 확정할 수 없다.

## 5. 개발 우선순위 [제안]

| 구분 | 기능 | 목적 |
|---|---|---|
| P0: 핵심 흐름 | 로그인·권한, 동아리 등록, 공연 등록·기본 목록·상세, 예매·결제·티켓 발급, 예매자 반영, 내 티켓·QR, 입장 처리, 기존 서비스 연결 | 공연 등록부터 관객 입장까지 한 흐름을 완성 |
| P1: 모바일 범위 완성 | 홈·홍보/소식·알림, 검색·필터, 지도·캘린더, 공연 수정·삭제, 동아리 프로필·이미지, 공연 집계, 마이페이지·설정 | 원문에 포함된 모바일 탐색·관리 기능 완성 |
| 보류·후속 | 동아리 찾기, PC, NFC·네트워킹 | 원문의 보류·선후 관계 유지 |

P1은 이번 모바일 범위에 포함된다. P0만 완료한 상태를 전체 모바일 구현 완료로 취급하지 않는다. 보류 기능을 다시 포함하면 일정과 완료 기준도 함께 수정한다.

## 6. 개발 순서와 일정 틀 [제안]

인원·마감일·기존 서비스 구조가 확인되지 않아 날짜나 소요 기간을 임의로 정하지 않는다. 먼저 아래 의존성을 맞추고 팀 협의로 착수일·목표일·구현 담당을 채운다.

| 단계 | 작업과 산출물 | 선행 조건 | 완료 기준 |
|---|---|---|---|
| M0: 계획·설계 정렬 | 본인이 개발계획·API/DB 초안·데이터 흐름·외부 연동 검토를 정리. 기능·정책과 프론트 연동 조건은 팀과 협의 | 이 계획서 | P0 관련 미정 사항과 API·DB 관계를 정리하고, 세팅 담당자에게 구조·연동 조건 전달 |
| M1: 회원·동아리 | 로그인·회원 유형·관리 권한, 동아리 등록 | M0의 회원·등록 결정 | 개인/동아리 기능 분기, 동아리 회원의 개인 기능 유지, 권한 제한 확인 |
| M2: 공연 등록·조회 | 공연 등록, 기본 목록, 상세, 포스터 처리 | M1, 공연·이미지 설계 | 등록한 공연을 관객과 주최 동아리가 조회하고 원문 필드 확인 |
| M3: 예매·결제·발권 | 예매·결제 상태, 티켓 발급, 동아리 예매자 반영 | M2, 티켓·결제 설계와 연동 준비 | 성공/실패/중복 결과에서 예매·티켓·예매자 정보 일치 |
| M4: QR·입장 | 티켓 정렬·QR, 검증·입장 기록, 기존 서비스 연결 | M3, 입장 정책·기존 서비스 연동 확인 | 유효/무효/중복 QR 처리, 중복 집계 방지, 입장 후 연결 확인 |
| M5: 동아리 관리 보강 | 공연 수정·삭제, 프로필·이미지, 내 공연 집계 | M2부터 시작 가능. 집계 완료는 M3·M4 필요 | 수정·삭제 정책 적용, 권한 제한, 예매·입장 수와 목록 일치 |
| M6: 탐색·개인 기능 | 홈·소식·알림, 검색·필터, 지도·캘린더, 마이페이지·설정 | 공연 탐색은 M2, 본인 내역은 M3 필요. 기능별 외부 연동 준비 | 모든 범위의 조회·설정 결과 확인, 탐색에서 상세로 연결, 본인 내역 일치 |
| M7: 모바일 통합 확인 | 관객·동아리 계정으로 전체 흐름 연결, 기존 기능 확인 | M1~M6 | 아래 모바일 완료 기준을 충족하고 공동 검토 |

M5·M6의 독립 작업은 선행 데이터가 준비된 뒤 병행할 수 있다. 지도 등 후순위 기능의 업체 선택이 미정이라는 이유만으로 모든 P0 작업을 막지는 않는다.

### 모바일 단계 완료 기준 [제안]

- 동아리 등록·공연 등록 → 관객 탐색·예매·결제 → 티켓 → QR 입장 → 기존 서비스 연결을 실제 연동 상태에서 확인한다.
- 결제 실패·결과 재수신, 무효 QR·중복 스캔에서도 개인·동아리 데이터가 맞는다.
- 동아리 계정에서도 본인 예매·티켓을 이용할 수 있다.
- 홈·검색·지도·캘린더·마이페이지·동아리 관리가 확정된 모바일 범위대로 동작한다.
- 기존 모바일 기능이 유지되는지 기존 서비스와 대조한다.
- 화면 연결만 된 시연과 외부 API·DB가 연결된 확인 결과는 구분해 기록한다. 모바일 완료 후 PC 계획을 구체화한다.

## 8. 본인의 백엔드 산출물과 다음 작업

본인이 이 계획서와 위 결정 사항을 바탕으로 다음 설계 산출물을 작성한다. API와 DB를 따로 확정하지 않는다. Supabase 세팅·배포는 이 작업에서 수행하지 않는다.

1. **개발계획서:** 이 문서의 기능 범위·흐름·우선순위·완료 기준을 팀과 맞춘다.
2. **데이터 흐름:** 예매/결제 상태 변경 → 티켓 발급 → 예매자 조회, QR 검증 → 입장 기록 → 개인/동아리 상태·집계 반영을 정리한다.
3. **API 명세·외부 연동 목록:** 기능별 요청·응답, 인증·관리 권한, 오류/상태 결과, 함수명·필드명 규칙을 작성한다. 외부 서비스의 필요 여부·후보·호출 주체·입력/결과·준비 조건을 함께 검토한다.
4. **DB 설계:** 회원·동아리·공연·티켓 종류·예매·결제·발급 티켓·입장 정보의 관계와 식별자 연결을 정리하고 ERD·테이블 정의를 작성한다. API 명세와 이름·형식·관계를 대조한다.
5. **구조 인계:** Supabase 세팅 담당자에게 테이블 관계·제약·접근 권한·외부 연동 준비 조건을 전달한다. 실제 프로젝트 생성·DB 적용·연결 검증은 세팅 담당자의 결과를 확인한다.

### 본인의 설계 검토 기준

- 개인 티켓과 동아리 예매자 목록이 같은 예매·티켓 관계를 참조하는가?
- 결제 성공·실패·중복 결과를 예매·티켓 상태와 일관되게 처리하는가?
- QR 중복 검증·입장 처리에서 기록과 집계가 맞는가?
- 본인 데이터 조회와 소속 동아리 관리 권한이 API에 반영되는가?
- 동아리 회원의 개인 기능과 입장 후 기존 서비스 연결이 빠지지 않았는가?
- 명세와 DB 설계의 이름·형식·관계가 맞고, 미정 항목을 임의로 확정하지 않았는가?

## 9. 근거와 검토 한계

- 노션 본문·회원 차이 표·텍스트 흐름도를 이 대화에서 확인했다. 외부 Claude 와이어프레임은 열어 검토하지 않았고, Figma 임베드는 로그인 요구로 내용을 확인하지 못했다. 상세 화면 구조는 미검토 상태다.
- 2026-10-07 확인한 로컬 `bandy`는 `main`의 커밋 없는 저장소이며 코드·원격 설정이 없었다. 기술 스택, DB, 기존 기능 구현 상태를 확인하지 못했다. 기존 서비스 자체가 없다는 의미는 아니다.
- Claude 검토에서 남은 핵심 미정 사항은 예매·결제 생성 순서, 동아리 등록 절차, 티켓 판매 수량 정책, 기존 서비스 연결 방식, 미검토 화면 자료다. 이 문서의 결정 목록에 반영했다.
- 이 작업의 산출물은 설계 문서다. API 구현, DB 생성, Supabase·외부 서비스 설정, 배포·실제 연결 검증은 수행하지 않았다. 개발계획서의 완료 기준은 앞으로 확인할 기준이며, 이미 통과한 검증 결과가 아니다.
